# Phase 16 — Web: Rule builder, default severities, allowlist

Skills: sentinel-nextjs-frontend, sentinel-rules-engine, sentinel-api-design, sentinel-security-hardening, sentinel-testing-workflow.

## Goal
Give the administrator full, safe control of detection logic: define rules like "≥5 failed logins in 10 minutes → medium, ≥20 in 10 minutes → high", edit default event severities, manage conditional overrides and the allowlist — with validation, previews, backtests, versioning, reset and audit.

## 16.1 Rules list (`/rules`)
Table: enabled toggle (admin), name, kind badge, summary sentence (generated: "Failed logins grouped by source IP: ≥5 in 10 min → medium; ≥20 in 10 min → high"), severities of tiers (colored with text), last fired (from findings), findings in 24 h / 7 d, built-in vs custom badge, "modified from default" badge, version. Filters: kind, enabled, built-in/custom, text, "noisy" (top by findings/day). Actions (admin): New rule, Duplicate, Reset to default (built-in), Disable, Delete (custom, confirm), Import/Export JSON (validated server-side; shows errors by path).

## 16.2 Rule editor (`/rules/new`, `/rules/[id]`) — the main work item
Two synchronised modes: **Form builder** (default) and **JSON** (advanced; validates against `/rules/schema`, live errors). Switching modes preserves state; invalid JSON blocks switching back with an explanation.

Form builder sections (react-hook-form + zod generated from the `/rules/schema` catalogue, server remains authoritative via `POST /rules/validate`, debounced):
1. **Basics**: name, id (auto-slug, editable only on create), description, enabled, tags, MITRE multi-select (static catalogue with names; labelled "indicative").
2. **What to match**: event types (grouped multi-select), optional **condition builder** (nested ALL/ANY/NOT groups; field picker with autocomplete from the field catalogue incl. `details.*`; operator list filtered by field type; value inputs by operator: text, list chips, CIDR list, regex with live syntax check and the safety rules explained; case-insensitive toggle). Shows a plain-English rendering (`describe`) of the conditions.
3. **How to group and count** (threshold): group-by multi-select (source IP, username, process, destination IP, file path, none = global), aggregate (`count` | `distinct count of <field>`), window mode (**sliding** | **fixed minute/hour/day**) with an inline explanation and a tiny diagram of the difference, cooldown.
4. **Tiers** (the user's key feature): a list of tier cards — each with `count`, `window` (value + unit: seconds/minutes/hours/days), `severity` (segmented control), `points`, `label`. Add/remove/reorder tiers (max 10). Live **sentence preview** per tier: *"If ≥ 20 failed logins from the same source IP occur within 10 minutes → HIGH (+30 points)"*. Inline warnings from the server (dominated tiers, identical windows) and errors per field. Example presets: "Brute force (5/20/50)", "Password spraying", "Burst detection (fixed per-minute)".
5. **Sequence / New-value / Field-match / Baseline-metric / Incident-meta** forms for the other kinds (steps editor with ordering and per-step counts; field + per + learning days; severity/points/cooldown; metric + subject + z/min_absolute tiers; meta conditions), all with the same preview/validation mechanics. Kind selector shown on create only.
6. **Actions**: create incident toggle, notify toggle, tags, scope: "exclude allowlisted events" (default on).
7. **Preview & backtest panel** (sticky): date-range selector (default last 7 days, max 30) → `POST /rules/preview` with the **unsaved** definition. Shows: total findings, by severity/tier, distinct groups, noise per day with a traffic-light heuristic ("≈ 1.7 findings/day"), a timeline histogram, top groups, and sample evidence events (drawer). A clear **"No data in this range"** and **"Too much data — narrow the range"** states. Preview is debounced and cancellable; never persists anything; labelled "Simulation on historical data".
8. **Save**: admin only; shows a diff (before/after JSON, human-readable summary of changed fields) in a confirm dialog; on success toast + version bump. Unsaved-changes guard on navigation. Built-in rules show "Reset to default" and "Compare with default" (diff view). **Version history** tab: list versions, view diff between any two, **restore a version** (creates a new version).
9. **Dry-run on save of high-impact changes**: if a change would have produced > N (default 100) findings in the last 24 h, warn before saving.

## 16.3 Default severities (`/severity`)
Three tabs:
1. **Event-type defaults**: table of every event type with description, current severity (select), points (number), enabled toggle (with warning "Disabled types are not stored — evidence is lost"), default value, "modified" badge, per-row reset; "Reset all to defaults" (typed confirmation). Changes batched with a Save bar and diff; audit on save. Shows **events in last 24 h per type** to show impact.
2. **Overrides** (conditional severity): ordered list with drag-and-drop **and** keyboard reordering (accessible), each with name, enabled, condition builder (same component as rules), resulting severity, builtin/modified badges, reset-to-default for built-ins, create/duplicate/delete custom. Shows the first-match-wins explanation and a **test box**: paste/pick an event (from recent events) → shows which default/override would apply and the resulting severity and `severity_source`.
3. **Apply to existing events**: explains that changes affect **new** events only; "Preview re-apply" (dry run: counts changed per severity before/after) → "Apply" (admin, typed confirmation, shows progress/result and audit note). Also holds **risk thresholds** (score → severity bands editor with validation: strictly increasing; live preview bar) and optional **recency decay** settings.

## 16.4 Allowlist (`/allowlist`)
Table: kind, value, scope (annotate / suppress alerts / lower severity), reason, created by/at, expires (countdown badge, "expired" greyed), enabled, **matches in the last 24 h** and suppressed count (so the effect is visible). Create/edit dialog: kind-specific input validation (IP, CIDR, username, command executable, event type, path), scope with plain-language consequences, **required reason**, optional expiry (presets 1 d / 7 d / 30 d / never — "never" shows a warning). Banner: "Allowlisted evidence is still stored and shown; it is excluded from alerts/incidents only when scope is *suppress alerts*." Deleting asks for confirmation. Everything audited.

## 16.5 Cross-cutting UI rules
Admin-only controls are hidden **and** disabled for viewers (viewers see read-only views with a "view only" note). All writes send CSRF header (client handles). Every form: label, help text, inline errors from server paths mapped to fields, `aria-describedby`, keyboard operable, no color-only meaning. All destructive or high-impact actions use `ConfirmDialog` (typed confirmation for bulk). Unsaved-change guards.

## 16.6 Tests
Vitest: tier editor (add/remove/reorder, unit conversion 10 minutes ↔ 600 s, sentence preview text exactly matches the user's example: *"If ≥ 5 failed logins from the same source IP occur within 10 minutes → MEDIUM"*, max 10 tiers); form↔JSON round trip lossless for every kind (property-style with fixtures from seeded rules); zod + server error path mapping to fields; condition builder (nested groups, operators per field type, regex live validation, depth limit, `describe` text); preview debounce/cancel and state rendering; diff dialog content; version restore; built-in reset; dominated-tier warning display; defaults table batching and reset; override reorder (mouse and keyboard); override test box result; re-apply dry-run → confirm flow requires typed confirmation; thresholds validation; allowlist reason/expiry validation; viewer read-only. Playwright (demo DB): **create the user's example rule end-to-end** (5→medium, 20→high, 10-minute window, group by source IP), run preview, see expected findings count on seeded attack data, save, see it in the list with the generated summary sentence; edit failed_login default severity to medium and verify new events use it after an engine cycle; add and reorder an override; create allowlist entry with reason and verify suppressed counter; reset a built-in rule to default.

## Gate
Green suites; the user's example rule is created purely through the UI and backtested; docs `docs/RULES.md` has screenshots-free step-by-step instructions for the builder.
